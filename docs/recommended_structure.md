# Рекомендуемая структура проекта (Feature-Sliced Design Lite)

Если бы я начинал этот проект с нуля или проводил глубокий рефакторинг, я бы предложил структуру, вдохновленную методологией **Feature-Sliced Design (FSD)**, но адаптированную для Next.js.

Текущая структура (`src/components/ui`, `src/components/business`...) уже неплоха, но по мере роста проекта она может стать запутанной, когда бизнес-логика смешивается с UI.

## 🏆 Предлагаемая структура

```
src/
├── app/                  # Next.js App Router (только роутинг и метаданные)
│   ├── (public)/         # Группировка публичных маршрутов
│   │   ├── page.tsx
│   │   └── about/
│   └── (auth)/           # Группировка маршрутов авторизации
├── shared/               # Переиспользуемый код, не привязанный к бизнесу
│   ├── ui/               # Базовые UI-кит компоненты (Button, Input, Modal)
│   ├── lib/              # Хелперы, утилиты, хуки (useClickOutside)
│   ├── assets/           # Иконки, картинки, шрифты
│   └── config/           # Константы, переменные окружения
├── entities/             # Бизнес-сущности (Данные + Базовое отображение)
│   ├── tariff/           # Сущность "Тариф"
│   │   ├── model/        # Types, Redux slices
│   │   └── ui/           # TariffCard, TariffRow
│   ├── user/             # Сущность "Пользователь"
│   └── article/          # Сущность "Новость/Статья"
├── features/             # Пользовательские сценарии (Действия)
│   ├── theme-switcher/   # Переключение темы
│   ├── auth-by-email/    # Форма входа по email
│   ├── calculate-cost/   # Калькулятор стоимости
│   └── feedback-form/    # Форма обратной связи
├── widgets/              # Композиция сущностей и фич (Крупные блоки)
│   ├── header/           # Шапка (Logo + Menu + ThemeSwitcher)
│   ├── footer/           # Подвал
│   ├── promo-section/    # Секция с промо
│   └── tariff-table/     # Таблица тарифов (TariffRow + FilterFeature)
└── views/ (или pages/)   # Сборка виджетов в готовые страницы
    ├── home-page/
    ├── business-page/
    └── company-page/
```

## 💡 Почему это лучше?

1.  **Shared/UI (UI Kit)**:
    - Здесь лежат _глупые_ компоненты. Они ничего не знают о Redux, тарифах или пользователях.
    - _Сейчас:_ Компоненты разбросаны, сложно понять, где чистый UI, а где логика.

2.  **Entities (Сущности)**:
    - Выделяет бизнес-объекты. Если вам нужно поменять отображение "Карточки тарифа", вы идете в `entities/tariff`.
    - _Сейчас:_ Таблица тарифов лежит в `components/tariffs`, а типы где-то в другом месте.

3.  **Features (Фичи)**:
    - Это действия. "Кнопка" — это Shared. "Кнопка Купить Тариф" — это Feature. "Форма входа" — это Feature.
    - Позволяет легко переиспользовать логику.

4.  **Слабая связность**:
    - Правило: **Модуль не может использовать модули выше себя**.
    - `Shared` доступен всем. `Entities` могут использовать `Shared`. `Features` могут использовать `Entities` и `Shared`. `Widgets` собирают всё вместе.
    - Это предотвращает циклические зависимости и делает код предсказуемым.

## 🚀 Как это применить к Storybook?

Структура Storybook при таком подходе зеркалит структуру папок:

- **Shared/UI** -> `UI (Buttons, Inputs...)`
- **Entities** -> `Entities (TariffCard, UserAvatar...)`
- **Features** -> `Features (AuthForm, CalcWidget...)`
- **Widgets** -> `Widgets (Header, Footer...)`
- **Views** -> `Pages (HomePage...)`

## Рекомендация для текущего проекта

Учитывая, что проект уже написан, **резкий переход на FSD будет долгим и болезненным**.

**Мой совет:** Оставьте текущую структуру как есть, но начните внедрять принципы FSD постепенно:

1.  Четко выделите **UI Kit** (папка `src/components/ui` уже есть — отлично!). Убедитесь, что там нет бизнес-логики.
2.  Выделяйте **Виджеты** (у вас это уже почти сделано: `navbar`, `footer`, `home/AppPromo`).
3.  Остальное временно считайте "Фичами/Сущностями".

Ваш текущий подход с разделением на `ui`, `components` (с логикой) и `widgets` — это упрощенная, но рабочая версия этой архитектуры, подходящая для проектов среднего размера.
